How it works.

Pipeline

Pull new leads from Dynamics 365 (OAuth2 + OData) → preprocess (32 features) → XGBoost score → business-rule overrides → write score, tier & reason back to CRM.

Model

XGBoost trained on 32,701 historical leads; out-of-time tested on 10,310. 32 engineered features across categorical, high-cardinality (target-encoded), numeric, and missingness-flag inputs.

Business rules

Order size ≥ 50 kW forces Hot tier — captures domain knowledge the model under-weights on rare large orders.

Production

Runs unattended every 30 minutes via Windows Task Scheduler; safety rails include a 5,000-lead cap per run, score-once policy, and incremental state tracking.

Key decisions.

Batch sync into CRM, not a separate dashboard.
Sales reps live in Dynamics — pushing scores into their existing tool drove adoption far better than building a parallel UI.
Business rules as a layer on top of ML.
Pure model scores under-call rare large orders. The 50 kW override captures domain knowledge the model can't learn statistically from few examples.
Score-once policy.
Locks in the score at lead intake instead of re-scoring on every edit — prevents noise from reps updating descriptions.
Rule-trigger reason field.
Telling reps why a lead is Hot ("order size 80 kW") turned a black-box score into something they trust and act on.
Out-of-time validation, not random split.
Tested on Feb–Apr 2026 data after training on Jun 2025 – Jan 2026 — mirrors how the model is actually used in production.

How it works.

Ingest

Drop a PDF in input/ (or POST to API) → GROBID parses it into TEI XML → custom parser cleans + marks sections → token-aware chunker (tiktoken, 800-token chunks) → BGE-large embeddings → Qdrant Cloud.

Retrieve

4-stage hybrid pipeline — vector search (top 20) + BM25 keyword search (top 20) → Reciprocal Rank Fusion (scale-invariant) → cross-encoder rerank (MiniLM) → top 5 to LLM.

Generate

Gemini 2.5 Flash by default · Flash Lite for simple queries · Mistral 7B (HF) as fallback · multi-key rotation · 24-hour query cache · per-call usage log.

Operate

Watchdog auto-ingests new PDFs · FastAPI exposes /ingest, /qa, /compare, /summarize · Streamlit primary UI, React frontend in development.

Key decisions.

GROBID as a service, not a library.
Wrapping a mature Java parser in Python would re-implement years of work badly. Running it as a Docker service keeps the pipeline lightweight and lets GROBID upgrade independently.
Hybrid retrieval — all four stages earn their place.
Vector alone misses exact terms ("ORR", "Pt/C 20%"); BM25 alone misses paraphrases; RRF merges them without normalising scores; cross-encoder rerank gives final precision on the top 10.
Two Qdrant collections.
chunks for retrieval, doc_records for paper-level operations (listing, similar-paper lookup). Payload indexes on doc_id / main_section / is_terminal turn filtered queries from full-scans into O(log n).
Multi-key Gemini rotation + Mistral fallback.
Free-tier rate limits would otherwise kill the system during heavy ingestion. Rotation + fallback + 24h cache keeps it usable end-to-end.
Terminal-section filtering.
References / Acknowledgements chunks are marked at parse time and excluded from retrieval — so the LLM can never accidentally cite a bibliography line as evidence.
Token-aware chunking with tiktoken (cl100k_base).
Exact token counts prevent silent overflows into Gemini; chunks respect section boundaries so context never bleeds across topics.

How it works.

Scrape

Selenium pulls high-resolution figure URLs from Google Patents → PyMuPDF renders the PDF at 300 DPI as fallback → BeautifulSoup extracts metadata, abstract, description, and claims.

Extract

Regex finds reference-number candidates in the Preferred Embodiment section → NLTK POS tagging filters out non-nouns and generic terms → produces ref_number → component_name mapping with low-confidence flags.

Annotate

Tesseract OCR locates reference numbers on each figure → Pillow draws component-name labels with semi-transparent backgrounds → saves annotated PNG alongside the original.

Answer

5-question Q&A pipeline — Q1/Q3/Q4 (owner / dates / jurisdiction) answered instantly from metadata; Q2 (invention summary) and Q5 (lab-reproduction guide) generated by Gemini 2.5.

Key decisions.

Two-tier figure scraping.
Selenium first — the hi-res D000xx URLs only load after Google Patents' JavaScript runs. PyMuPDF rendering at 300 DPI as a fallback guarantees 100% figure coverage even when scraping fails.
Hybrid Q&A router — LLM only where it earns its place.
Q1/Q3/Q4 are pure metadata lookups; spending a Gemini call on them would waste tokens and add latency. Q2 (summary) and Q5 (reproduction guide) are where language quality matters, so they go to Gemini.
NLTK POS filtering for component names.
Raw regex matches on reference numbers pick up generic words ("layer", "film", "substrate"). POS tagging filters down to genuine noun phrases; low-confidence picks are flagged with (?) so engineers can verify rather than trust blindly.
Filesystem-per-patent, no database.
Each patent gets its own folder with metadata.json, abstract.txt, description.txt, claims.txt, and figures/. Portable — zip the directory and the entire patent corpus moves with it. No schema migrations, no DB to host.
Every stage is independently callable.
Component extraction and figure annotation each have their own REST endpoint, so engineers can re-run a single stage without re-scraping. Helpful when tuning the OCR / NLTK steps on already-scraped patents.
Async background scraping with in-memory job locks.
Scraping is slow (Selenium + figure downloads). Kicked off as a background thread; frontend polls /api/status. A threading.Lock prevents the same patent from being scraped twice concurrently.
